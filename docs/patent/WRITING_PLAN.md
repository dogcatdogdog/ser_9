## 2. 字数预算（总计 ≈10,000 字，区间 9,000–11,500）

| 章节 | 字数 | 占比 |
|---|---|---|
| 一 发明名称 | 60 | 0.6% |
| 二 技术领域 | 200 | 2% |
| 三 背景技术 | 1,400 | 14% |
| 四 要解决的技术问题 | 350 | 3.5% |
| **五 技术方案** | **3,400** | **34%** |
| **六 效果和优点** | **1,700** | **17%** |
| 七 附图及说明 | 350 | 3.5% |
| 八 具体实施方式 | 2,600 | 26% |
| 附录 创造性评述（选填） | 500 | — |

> 预算控制：§五+§八（技术方案与实施例）合计 ≥60%，因为**这两章决定专利的清楚充分性**；
> §三 只占 14%——背景写得越长越容易踩到前案的坑。

## 3. 写作顺序（不按章节顺序写）

```
① §五 技术方案   —— 先固化技术骨架与术语（其余章节都要引用它）
② §八 具体实施方式 —— 紧接着写可重现材料（与代码/数据核对）
③ §三 背景技术   —— 回看 §五，倒推"必须解决的缺陷"，避免写出解决不了的缺点
④ §六 效果和优点 —— 每条对齐 §四 的问题与 §五 的手段
⑤ §四 / §二 / §一 —— 收口：问题、领域、名称
⑥ §七 附图说明   —— 最后统一图号与图注
⑦ 附录(选填)
```
理由：背景（§三）**后写**能保证"指出的每个缺陷都有本方案对应"，这是交底书最常见的失分点。

## 4. 流程（含检查与审阅）

| 阶段 | 动作 | 产出 | 出口检查 |
|---|---|---|---|
| **R0 冻结** | 场景/数据/图定稿 | `SCENARIO.md`、9 图、数据 JSON | ✅ 已完成：图数据=表数据 |
| **R1 起草** | 按 §3 顺序写正文 | `docs/patent_disclosure.md` 初稿 | 每节字数在预算 ±20% |
| **R2 自检** | 走 §5 检查清单 | 修订稿 | 清单全绿 |
| **R3 数据核对** | 正文每个数字 → 出处（§6 机制） | `DATA_CHECK.md` | 100% 可溯源、无手抄 |
| **R4 术语/编号一致性** | 全文术语与图号校验 | 修订稿 | 术语表命中、图号连续 |
| **R5 审阅** | ①代理人视角（清楚充分性/权项支持）②导师/负责人 review | 审阅意见 | 意见全部闭环 |
| **R6 定稿** | 版本冻结 + DEVPLAN 勾选 | 定稿 + commit | 硬节点 W9 前完成 |

## 5. 自检清单（R2，逐条打勾）

**技术准确性**
- [ ] 全文术语统一为"**等效电量距离（EED）**"，首次出现给公式与 α/β 定义
- [ ] 每个公式与 `A3_REQUIREMENTS §3.2` / `energy_model.py` 一致
- [ ] 每个算法步骤与 `solver.py` / `heuristic.py` 的实现一致（不写未实现的功能）

**专利质量**
- [ ] §三 的每个缺陷，§四 都有对应问题，§五 都有对应手段（三点对齐）
- [ ] 区别技术特征明确，且不宣称前案已有的内容
- [ ] 附图标记均在正文被提及；正文提到的标记都在图中出现
- [ ] 无超范围宣称（对照 `SCENARIO.md §5` 红线逐条核对）

**数据**
- [ ] 每个数字能在 `results/table_20260819_105511.md` 找到（或 JSON 脚本产出）
- [ ] 数值口径正确（gap 的分子分母、负值含义、PyVRP 为时限截断）
- [ ] 表格/图与正文数字一致（图9 与 §6.2、图8 与 §6.3）

**表达**
- [ ] §五 按实施顺序、每步有输入/判定/输出
- [ ] §八 达到"本领域技术人员可重现"（机型、数据、步骤、seed、结果齐全）
- [ ] 中文表述、无口语化；专业名词首次出现给全称
