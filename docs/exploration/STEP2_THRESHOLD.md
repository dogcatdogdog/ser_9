> 日期 2026-09-10　分支 `worktree-tw-feasibility`　数据：`step2_threshold.json`、`step1_perf_clean.json`

## 1. 结论

**精确模式覆盖整个 MVP 边界 n ≤ 20，且在 10 并发下仍满足服务预算。**

预算依据（对齐 `a3_rust/src/http.rs`）：求解时限 5.0 s（取 80% 作可用预算 = 4.0 s）；
服务内存按 2 GB 计；并发档位取 1 / 5 / 10（W8 硬化时验证过 10 并发 20 点）。

| n | 耗时中位 | 耗时最差 | 内存 | 并发1 | 并发5 | 并发10 |
|---|---|---|---|---|---|---|
| 14 | 0.053 s | 0.055 s | 2.5 MB | ✅ | ✅ | ✅ |

| 16 | 0.112 s | 0.122 s | 9.5 MB | ✅ | ✅ | ✅ |
| 17 | 0.206 s | 0.232 s | 19.1 MB | ✅ | ✅ | ✅ |

**阈值：并发 1 / 5 / 10 均为 n = 20**（即 MVP 上限内无需降级）。

| 实现 | n=15 | n=18 | n=20 |

| 原纯 Python 三重循环（`exact.py` 同款） | 1.62 s | 18.5 s | 96.5 s ❌ |

## 3. 两处必须修正的此前记录

### 3.1 计时误用（我的错误）

`run_adaptive_validation.py` 用 `tracemalloc` 包裹计时，得出"n=15 需 19.7 s"。
**该数字失真**：tracemalloc 追踪每次浮点分配，对纯 Python 实现的惩罚（实测 11×）远大于 numpy（3×）。
纯净计时下 n=15 只需 **1.62 s**。**"只能精确到 n≤15"的结论据此作废。**

### 3.2 电量约束不改变最优解（重要理论修正）

**结论**：在本建模下，电量约束（累计能耗 ≤ 电池容量）**不改变最优序列**，只是一个可行性闸门。

**论证（三行）**：目标函数即总能耗；沿访问顺序累计能耗**单调不减**，
故约束"每个中间点累计 ≤ cap"等价于"终点累计（即总能耗）≤ cap"。
于是：若 `cap ≥ 最优总能耗`，则约束版最优 = 无约束最优；否则无可行解。

**数值验证**：6 实例 × 3 档电池容量（5000/2000/1500 Wh）= 18 组，
带电池精确解与无约束精确解的**序列 18/18 完全相同**，目标值仅差常数因子 α（单位不同：m vs Wh）。

**由此修正 `WMLP_INSIGHT.md` §2 的表述**：先前写的
"此前从未算出过该问题的真实最优"**不成立**——MVP 已有的
`exact.py::solve_energy_exact_dp`（无电池版）给出的序列即真实最优序列。
带电池版的真实增量只有两项：
1. **可行性判定**（该实例是否存在满足电量约束的解）；
2. **性能**（把可在线求解的规模从 n≤15 扩到 n≤20，见 §1）。

## 4. 由此确立的技术主张（供交底书使用）

可验证的事实（均有单测与数据）：

1. **覆盖范围**：在 5 s 时延 / 2 GB 内存、10 并发下，**n ≤ 20 全范围在线精确最优**；
   而原实现（`exact.py` 上限 `MAX_DP_POINTS = 15`）只到 n ≤ 15。
2. **加速来源**：按已访问点个数**分层推进**（内存 $O(\max_k\binom{n}{k}\cdot k)$ 而非 $O(2^n n)$）
   + numpy 批量转移 + **可采纳下界剪枝**（上界取自启发式解）。
3. **正确性**：与暴力枚举、原参照实现**逐位一致**（n=5~10 多实例、多分布）；
   下界可采纳性对 n=5,6 的**每个状态**逐一验证。
4. **降级模式的质量界**：启发式在 70 实例上 **65.2% 直接命中最优、97.1% 距最优 ≤ 2%**。

## 5. 边界与诚实声明

- 精确模式在 **n > 20 会越界**（内存 ~2×/n：外推 n=21 ≈ 280 MB），
  超出 MVP 边界时应走降级模式。
- 剪枝的上界来自启发式解；上界越紧剪枝越强，故**启发式与精确模式是协同关系**，
  而非互斥的两条路。
- 本节全部数字可由 `run_step2_threshold.py` 与 `run_exact_perf.py --clean` 复现。
